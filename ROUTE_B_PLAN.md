## 1. Context & Motivation

VAEB currently supports **Route A** (deposit flow): an agent deposits BTC to a bridge-designated address, and the existing scanner → proof generator → Sui light client pipeline handles verification and mints BTCVC.

**Route B** (self-custodial flow) lets agents register their **own** BTC addresses with the bridge scanner. Instead of depositing to a bridge-operated address, the scanner monitors the agent's self-custodial address and handles proof generation + BTCVC minting when deposits appear.

Two mint_to modes are required (from different client requests):
- **Route B-1 (Global Vault):** All BTCVC mints to a single shared vault address on Sui
- **Route B-2 (Per-Address):** Each agent specifies their own Sui destination address

**Constraint:** Do NOT modify any bridge code (scanner, proof generator, Sui light client contract). All changes are in the VAEB layer only.

## 2. Audit Findings

### 2.1 Lightclient-Custody Scanner

Repo: `https://github.com/vishwanetwork/lightclient-custody`

**Answer: The light client has NO white-label / self-custodial address concept.**

The scanner manages monitored BTC addresses through two separate storage systems:

#### Storage System A: `BtcAddress` Table (Peewee ORM)
- Used by: `Btc2SuiBTCvcMonitor`, `Btc2EvmBTCvcMonitor`
- Fields: `id`, `type`, `address` (unique), `last_block_height`, `status`, `create_by`, timestamps, `del_flag`
- **NO per-address `mint_to`** — the Sui monitor uses a global `self.config['contract']['mint_to']`
- Addresses loaded from YAML config at startup via `_load_custody_address()`

#### Storage System B: `MONITOR_CUSTODY_ADDRESS` Table (raw SQL)
- Used by: `BtcCustodyAddressMonitor` (generic monitor)
- Fields: `CUSTODY_ADDRESS` (PK), `CUSTODY_CHAIN`, `LAST_BLOCK_HEIGHT`, `TO_ADDRESS`, `TO_CHAIN`, `VAULT_KEY_ID`
- **SUPPORTS per-address routing** — `BtcCustodyAddressMonitor` uses `addr_info.to_address` for each mint call
- The generic monitor handles Sui chain (lines 88-127 of `btc_monitor.py`) via `vault_key_id` → provider lookup

**Key code evidence (btc_monitor.py:110-117):**
```python
if tx_amount > 0:
    result = await provider.mint(
        to_address=addr_info.to_address,   # <-- Per-address routing!
        amount=abs(tx_amount),
        proof=groth16_proof['proof'],
        public_inputs=groth16_proof['public_inputs'],
        txid=txid
    )
```

#### Scanner DB Configuration
- Path controlled by `STORE_PATH` env var (defaults to `:memory:`)
- Uses Python `sqlite3` library
- `Store.init_address()` does `INSERT OR IGNORE INTO MONITOR_CUSTODY_ADDRESS`
- `Store.get_all_address(chain)` retrieves all addresses for a given chain

#### What Does NOT Exist
- No API endpoint for dynamic address registration at runtime
- No concept of address ownership (bridge-owned vs user-owned)
- No whitelist/allowlist for BTC addresses
- No address approval workflow or access control
- All addresses are treated identically by the scanner

```

Agent calls: init_btc_payment(amount_btc)
```

- Tool routing: `handlers.ts:handleToolCall()` → `btcTools.handle()` → individual handlers
- No database infrastructure in VAEB (no SQLite, no ORM, no persistent state)

## 3. Architecture Design

### 3.1 Integration Target

The `MONITOR_CUSTODY_ADDRESS` table is the correct integration target because:
1. It already supports per-address `TO_ADDRESS` routing (required for Route B-2)
2. `BtcCustodyAddressMonitor` already handles Sui chain via provider system
3. Inserting into this table is "using the scanner's data interface," not modifying its code
4. `INSERT OR IGNORE` semantics provide safe, idempotent registration

### 3.2 Connection Strategy

VAEB connects to the scanner's SQLite database via `better-sqlite3` (Node.js native module):
- Connection path from `SCANNER_DB_PATH` env var
- `PRAGMA journal_mode = WAL` enables concurrent read/write (scanner reads, VAEB writes)
- Lazy initialization — DB connection created only when a self-custody tool is first invoked
- `CREATE TABLE IF NOT EXISTS` on connect — safe against fresh or existing DBs

### 3.3 Why `better-sqlite3`?

- Synchronous API matches VAEB's existing handler patterns (all tool handlers are `async` but don't depend on async DB drivers)
- Ships prebuilt binaries for macOS ARM/Intel and Linux x64/ARM
- WAL mode support for safe concurrent access with the Python scanner process
- Standard choice for Node.js SQLite (30k+ GitHub stars, actively maintained)

## 4. Privacy Model

### 4.1 The Problem

The ZK proof system ensures the Sui light client verifies BTC deposits **without revealing depositor identity on-chain**. If VAEB maintains a publicly queryable registry mapping `agent_id → BTC address`, anyone can:
1. Look up which BTC addresses are registered
2. Query the BTC blockchain for full balance + transaction history of those addresses
3. Link the agent identity to their BTC holdings

This defeats the purpose of using ZK proofs.

### 4.2 The Solution: Commitment-Based Tracking

**What goes into the scanner DB (infrastructure-internal):**
- `CUSTODY_ADDRESS` (BTC address)
- `TO_ADDRESS` (Sui mint destination)
- `TO_CHAIN`, `VAULT_KEY_ID`, `LAST_BLOCK_HEIGHT`
- **NO agent identity, NO ownership information**

**What VAEB stores locally (in-memory, never exposed via API):**
- A commitment hash: `sha256(agent_wallet_address + btc_address + random_salt)`
- The commitment store is a `Map<hash, {createdAt, salt}>`
- This is private to the VAEB process — no MCP tool exposes the full store

**What the agent receives:**
- `commitment_hash` — proof of registration
- `salt` — random 32 bytes, must be saved for future verify/unregister operations

### 4.3 Access Pattern: Prove-You-Know

- `verify_btc_registration(btc_address, agent_wallet_address, salt)` — agent proves it registered an address by providing the preimage
- `get_self_custody_status(btc_address)` — requires knowing the address (cannot enumerate)
- **No `list_all_registrations` endpoint** — cannot discover other agents' addresses
- `unregister_btc_address(btc_address, agent_wallet_address, salt)` — requires commitment proof

## 5. New MCP Tools

### 5.1 `register_btc_address`

**Description:** Register a self-custodial BTC address for automatic bridging to Sui.

**Parameters:**
| Param | Required | Description |
|-------|----------|-------------|
| `btc_address` | Yes | The agent's own BTC address to register for monitoring |
| `agent_wallet_address` | Yes | Agent's wallet address (for commitment generation) |
| `sui_mint_to` | No | Sui address for BTCVC minting. Omit for global vault (B-1), provide for per-address (B-2) |

**Returns:**
```json
{
  "success": true,
  "btc_address": "bc1q...",
  "mode": "per-address",
  "sui_destination": "0x...",
  "commitment_hash": "a1b2c3...",
  "salt": "d4e5f6...",
  "is_new_registration": true,
  "message": "BTC address registered for self-custodial monitoring...",
  "instructions": { "step1": "...", "step2": "...", "step3": "...", "step4": "..." }
}
```

### 5.2 `unregister_btc_address`

**Description:** Remove a registered address from scanner monitoring. Requires original salt.

**Parameters:**
| Param | Required | Description |
|-------|----------|-------------|
| `btc_address` | Yes | The BTC address to unregister |
| `agent_wallet_address` | Yes | Must match registration |
| `salt` | Yes | The salt from registration |

### 5.3 `verify_btc_registration`

**Description:** Prove-you-know verification. Agent proves its own registration with original salt.

**Parameters:**
| Param | Required | Description |
|-------|----------|-------------|
| `btc_address` | Yes | The BTC address to verify |
| `agent_wallet_address` | Yes | Must match registration |
| `salt` | Yes | The salt from registration |

**Returns:** Registration status + scanner monitoring status (`monitoring`, `not_in_scanner`, `db_unavailable`)

### 5.4 `get_self_custody_status`

**Description:** Check monitoring and blockchain status for a specific BTC address.

**Parameters:**
| Param | Required | Description |
|-------|----------|-------------|
| `btc_address` | Yes | The BTC address to check |

**Returns:** Scanner monitoring info (`to_address`, `to_chain`, `last_block_height`) + blockchain info from mempool.space (`balance_sats`, `tx_count`, `network`)

## 10. Known Limitations & Future Work

### 10.1 In-Memory Commitment Store

The commitment store is in-memory. Server restarts lose all commitments, making verification/unregistration impossible for previously registered addresses. The scanner continues monitoring regardless — this only affects the VAEB-side prove-you-know interface.

**Future:** Persist commitments to a separate local SQLite file (not the scanner DB).

### 10.2 Scanner Scheduling

The `BtcCustodyAddressMonitor` is registered in MonitorFactory but **not currently scheduled** in the scanner's `start.py`. The bridge operator must enable it for Route B addresses to be actively monitored.

**Bridge operator action required:** Add to `start.py`:
```python
scheduler.add_job(
    MonitorFactory.create(MonitorType.BTC_CUSTODY).start,
    "interval",
    seconds=180,
    id="monitorBtcCustody",
    max_instances=1,
)
```

### 10.3 Sui Address Validation

The `sui_mint_to` parameter is not validated for Sui address format. The scanner will fail to mint if the address is invalid. Sui address validation can be added later.

### 10.4 `VAULT_KEY_ID` Configuration

The `VAULT_KEY_ID` must match a configured provider/signer in the scanner's infrastructure. VAEB takes this from env config but cannot verify it's valid without access to the scanner's provider registry.

### 10.5 Multi-Process SQLite Contention

With WAL mode, concurrent reads and writes are safe. However, under heavy load (many simultaneous registrations), SQLite's write lock could cause brief contention. For production scale, consider migrating to PostgreSQL or a registration API.
